# Комплект передачи проекта PostgreSQL

Учебный проект «Подключение сервиса заказов». Редакция комплекта 0.2. Среда проверки — `master3`, база `course`. Статус комплекта — на рассмотрении. Область изменения — профиль подключения приложения через PgBouncer.

## Д-01. Записка для владельца сервиса

Веб-приложению предлагается использовать маршрут ПОДКЛ-01 с повторным использованием серверных соединений. Для перехода владелец сервиса согласует изменение профиля подключения и выделяет исполнителя прикладной проверки. Платформа подтверждает доступность нового входа, а владелец сервиса подтверждает прохождение штатной операции и допустимое ожидание соединения по согласованному профилю нагрузки.

Решение, запрашиваемое у владельца сервиса, — допустить изменение профиля после проверки ПР-01. Переход остаётся запланированным до фиксации результата в протоколе. Рабочая запись по ПР-01 относится к учебной проверке маршрута, а допуск трафика оформляется отдельным решением.

## Д-02. Техническое описание

**ПОДКЛ-01. Реестр клиентских входов, редакция 0.2.** Вход веб-приложения — `192.168.0.35:6432`, база `course`, роль `course_app`, TLS с проверкой подлинности сервера. Приложение получает секрет и доверенный CA по принятой процедуре выдачи доступа. Значения для Windows используются в профиле DBeaver преподавателя.

PgBouncer принимает клиентское соединение, а его запись `course` направляет запросы к `rw:5432` во внутренней сети Compose. Это внутренний адрес следующего компонента. Подключение приложения описывается внешним адресом из ПОДКЛ-01. Прямой диагностический вход через HAProxy имеет собственное назначение и указывается отдельно.

## Д-03. Карточка передачи в эксплуатацию

**Кандидат карточки, редакция 0.1.** Дежурный проверяет веб-путь на `192.168.0.35:5432`, база `course`, роль `course_app`. Этот фрагмент сохранён в качестве входных данных для проверки согласованности комплекта.

**Согласованный текст для редакции 0.2.** Дежурный проверяет веб-путь по записи ПОДКЛ-01 из Д-02. При подключении фиксирует среду, проверяемый клиентский вход и полученный результат. При недоступности входа передаёт платформенной команде время и характер ошибки, а владелец сервиса определяет влияние на операции приложения. Прямой адрес PostgreSQL используется только как отдельный диагностический маршрут с собственным результатом.

## Д-04. Карточка доказательства ПР-01

Проверяемое утверждение — роль `course_app` через клиентский вход ПОДКЛ-01 подключается к `course` и может выполнить контрольное чтение. Метод — исполнить запрос из материала преподавателя, используя клиентский профиль с проверкой имени сертификата. Результат относится к указанной среде и редакции Д-02.

При записи результата указываем внешний адрес из профиля клиента, дату и время UTC, эффективные базу и роль, признак recovery и результат чтения. Внутренний адрес из SQL можно приложить для диагностики в копию для платформенной команды.

Начальный статус ПР-01 — «ожидает проверки». После прогона исполнитель добавляет наблюдаемый результат, место хранения доказательства и статус. Запись утверждения о переводе приложения на новый профиль оформляется владельцем после принятия решения по Д-01.

**Пример заполнения ПР-01.** 3 ноября 2026 года в 11:36:44 UTC проверено подключение к `192.168.0.35:6432` с `sslmode=verify-full`. PostgreSQL вернул `course`, `course_app`, `in_recovery=false` и `can_read_orders=true`. Источник доказательства — результат запроса ПР-01 из материала преподавателя. Статус проверки маршрута в среде `master3` для редакции 0.2 — «пройдено».

## Д-05. Ведомость передачи

Передаваемая редакция связывает Д-01, Д-02, обновлённую Д-03 и протокол Д-04. Ответственный за выпуск комплекта сверяет ссылки, версии, права доступа к приложениям и статусы открытых решений. Эксплуатация подтверждает получение инструкции и доступность способа диагностики. Владелец сервиса подтверждает решение о переходе. После принятия закрепляется версия комплекта, по которой работали стороны.
